sign-24-1: Chunked Reed–Solomon encoding reveals the signing witness

SeverityCritical
Scopeimplementation
StatusConfirmed
AffectedSigurd-128, -256, and -512 reference implementations
DiscoveryModerate
ExploitationWitness recovery and accepted fresh-message forgeries from 4–8 ordinary signatures in independent tests
CreditGuoxiao Liu (Tsinghua University); independently Martin Feussner, with OpenAI Codex (Daybreak Blue) assistance; independently Markku-Juhani O. Saarinen markku-juhani.saarinen@tuni.fi, with AI assistance
Date2026-09-25

Original source: Feussner's pqc-forum post and attached analysis Follow-up source: Sigurd team's confirmation and repair

The specification's vector commitment pads the witness with fresh random tail elements and applies one Reed–Solomon encoding. The submitted RS_encode instead divides the input into 32 independently encoded chunks (sig_core.c:640–745 in Sigurd-128; the same structure appears in the other reference sets). Early chunks contain only the unchanged witness prefix; the fresh tail cannot hide their evaluations. Signatures expose selected encoded-witness symbols, so openings accumulated across signatures interpolate those chunks. The public syndrome then determines the short remaining witness suffix. An independent whole-scheme witness recovered all 217/458/946 blocks from 4–8 ordinary signatures and forged a fresh message accepted by each submitted verifier; changing one recovered one-hot block made the control forgery reject. The flaw is in the submitted encoding, not the specified single-code construction.

The Sigurd team confirms that Guoxiao Liu first disclosed the issue privately and that Feussner and Saarinen found it independently shortly afterward. The frozen archive above remains the target of this finding.

Proposed fixes

The Sigurd team's response proposes replacing the 32 short codes with one global Reed–Solomon code in every parameter set, regenerating the KATs, and making the evaluation domain explicit. This section records the proposal without evaluating it. The post gives the updated code at github.com/QinLangT/Sigurd, which was not evaluated.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

make -C sign-24 exploit
tools/reproduce.sh sign-24

The independent driver queries sig_sign for ordinary signatures, parses only public transcripts, interpolates witness-only chunks, solves the remaining public-syndrome system, and calls the submitted Prover with the recovered witness. The original forum analysis reports broader 35-key testing; our witness tests two different keys at each level.

sign-24-2: Zero 16-bit challenge exposes the signing witness

SeverityCritical
Scopeimplementation
StatusConfirmed
AffectedSigurd-128, -256, and -512
DiscoveryModerate
ExploitationAn unmodified Sigurd-128 signer naturally reached zero after 3,458 same-key signatures in one test stream, exposing the witness; the expected query count is about 2^16
CreditMarkku-Juhani O. Saarinen markku-juhani.saarinen@tuni.fi, with AI assistance
Date2026-10-06

Follow-up source: Sigurd team's 2026-10-10 reply

The submitted implementation takes zeta from a 16-bit expansion word without excluding zero (Sigurd-128/sig_core.c:1711–1728, Sigurd-256/sig_core.c:1717–1734, and Sigurd-512/sig_core.c:1717–1733). The specification does not prescribe this scalar width or a zeta-scaled mask; its extension-field requirement is ιτ > λ precisely so the challenge and masking space is sufficiently large (physical p. 17). The code's final public response is G = E + zeta * F (Sigurd-128/sig_core.c:1408–1452). When zeta=0, masking term F disappears. The public response, public transcript, one-hot witness-block constraints, and public syndrome then form a linear system for the signing witness. Under the intended random-oracle interpretation of the XOF word, each signature has probability 2^-16 of this event. The signing and verification paths do not resample or reject zero. A recovered witness suffices for signing independently of the secret seed.

In a natural run, the unmodified Sigurd-128 signer reached zeta=0 on the 3,458th signature of one same-key worker stream. Its submitted verifier accepted that signature, and a solver using only the public key, message, signature and derived transcript recovered the exact witness, checked against the secret kept separately. The run used parallel worker streams sharing that key; 3,458 is the count in the successful stream, not the aggregate across workers. No fresh-message forgery was executed. Independently, forced-zero test builds at all three levels yielded full-rank systems and exact witness recovery (ranks 1302/1302, 2748/2748 and 5676/5676). Same-seed nonzero controls were inconsistent and yielded no witness. The natural run confirms the trigger at 128; the higher levels are supported by source identity and forced-zero tests, not a natural long run.

Proposed fixes

The Sigurd team's 2026-10-10 reply says its revised implementations take the first nonzero challenge word and make that rule explicit in the revised specification. It reports unchanged test vectors. The revision is recorded without evaluation. The reply gives the updated code at github.com/QinLangT/Sigurd, which was not evaluated.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

bash sign-24/reproduce_zero_zeta.sh
python3 sign-24/reproduce_natural_zero.py

Both wrappers build only in fresh temporary directories, with no changes to the submitted source tree. The first runs forced-zero and unforced controls at every level; the second uses up to 14 native workers to find a natural zero at 128. solve_zero_zeta.py receives only the public-equation file, and a separate file is used solely to check its recovered answer.

sign-24-3: Signing rebuilds the public state with secret-dependent control flow

SeverityLow
Scopeimplementation
StatusConfirmed
AffectedSigurd-128, -256, and -512, reference and optimized implementations
DiscoveryModerate
ExploitationSource inspection and execution profiling establish repeatable control flow depending on the long-term witness; no timing or cache observation, witness recovery, or forgery is demonstrated
CreditLK-PQC-Hunter (NGCC PKC Forum sender), using the LKQ PQC Hunter automated tool
Date2026-10-17

Original source: LK-PQC-Hunter's PKC Forum post

Every signing operation calls sig_build_public_state_direct, which expands the secret e_seed into the long-term error vector e and evaluates the public matrix on it. Inside the public-matrix loop, all six submitted implementations branch on e_bits[col] before conditionally updating y_bits (Reference_Implementation/Sigurd-128/sig_core.c:567,589–592; corresponding reference lines 573,595–598 at 256/512; optimized lines 2271–2274, 2120–2123 and 2324–2327). The branch condition is therefore secret and repeats under every signature made with one key. Replacing the conditional update with a masked or unconditional XOR is a local implementation change.

The forum post reports callgrind profiles in which the body count changes when only the secret portion of a hybrid key changes and remains stable across messages and signing randomness for one key. Its statement that this count equals the Hamming weight of e is not literal: random_e sets exactly one position in each six-coordinate block, so the weight is fixed. Because the secret branch is nested under the public matrix-bit branch, the count is instead a public-matrix-weighted function of the secret support. This correction does not remove the secret-dependent control flow. No externally observable timing or cache channel, and no route from the aggregate counts to key recovery, was demonstrated; the finding is Low under the side-channel policy.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

python3 sign-24/reproduce_secret_branch.py

The certificate checks all three reference and all three optimized sources for the fixed-weight secret expansion, the signing-time state reconstruction, and the conditional update on e_bits. It does not replay the reporter's callgrind measurements.

sign-24-4: Field multiplication indexes 64K-entry tables with secret operands

SeverityLow
Scopeside-channel
StatusConfirmed
AffectedSigurd-128, -256 and -512; reference and optimized implementations
DiscoveryTrivial
ExploitationLocal cache or address trace of witness- and mask-dependent table indices during signing; no recovery demonstrated
CreditMarkku-Juhani O. Saarinen markku-juhani.saarinen@tuni.fi, with AI assistance
Date2026-11-15

Every GF(2^16) multiplication in the prover is a logarithm-table product: mul_gf2_16 returns early if either operand is zero and otherwise computes gf_exp_table[gf_log_table[a] + gf_log_table[b]] (sig_core.c:184–201). The Reed–Solomon encoder has its own copy (rsencode.c:116–124), and the optimized trees use the same construction. Each table has 2^16 16-bit entries.

Signing multiplies and encodes the embedded witness and the per-signature masks with these functions. The table addresses and the zero test therefore depend on secret operands, and with 128 KB tables a cache-line observation narrows the logarithm of an operand considerably. This is separate from the control-flow dependence of sign-24-3. No recovery was built.

Constant-time fix (moderate): use carry-less multiplication, or a bit-sliced multiplier with masked reduction.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

d=sign-24/Implementations/Reference_Implementation/Sigurd-128
sed -n '184,201p' "$d/sig_core.c"; sed -n '116,124p' "$d/rsencode.c"

This is a source witness.

sign-24-5: Signature deserialization under-checks the length and over-reads a short signature

SeverityLow
Scopeimplementation
StatusConfirmed
AffectedSigurd-128, -256 and -512; reference and optimized implementations
DiscoveryTrivial
ExploitationOut-of-bounds read of a caller-supplied short signature during verification; no disclosure shown
CreditLK-PQC-Hunter (NGCC PKC Forum sender), using the LKQ PQC Hunter automated tool
Date2026-11-20

Original source: LK-PQC-Hunter's PKC Forum post

sig_verify passes the caller's signature length to sig_deserialize_signature (SIG_AlgorithmInstance.c:571 in the reference Sigurd-128). That function first requires only the root hashes, two raw polynomials and 4 bytes (:359): 108, 452 and 1,156 bytes at the three levels. It then unpacks 2*SIGMA_REPETITIONS + 6 + N_PRIME_LEN more polynomials and the 4-byte proof-hash count at fixed offsets (:364–392) before it checks the length again (:398). That prefix is 8,468, 22,500 and 84,932 bytes, so any signature length between the two bounds is read out of bounds. The other five trees have the same code.

Under AddressSanitizer, signatures in heap buffers of exactly the entry bound, and one byte short of the fixed prefix, gave heap-buffer-overflow reads in all six trees. An honest Sigurd-128 signature verified at full length and overflowed when cut to 108 bytes. Lengths below the entry bound and the full prefix were rejected cleanly. Only signature bytes are read out of bounds; the destination arrays are fixed-size. Callers that pass complete signatures are unaffected.

sign-24-6: Verification uses static workspaces and fails, crashes or accepts an altered message under concurrent calls

SeverityHigh
Scopeimplementation
StatusConfirmed
AffectedSigurd-128, -256 and -512, reference and optimized implementations (source); run for Sigurd-128; altered-message acceptance and crashes in the optimized implementation only
DiscoveryModerate
ExploitationIn the optimized implementation, while other threads verify a genuine signature, a concurrent verification of that signature on a one-bit-altered message returned success in 0.1% to 0.6% of calls, depending on the test driver; honest signatures are rejected in both implementations
CreditLK-PQC-Hunter (NGCC PKC Forum sender), using the LKQ PQC Hunter automated tool; optimized-tree crashes and altered-message acceptance by Markku-Juhani O. Saarinen markku-juhani.saarinen@tuni.fi, with AI assistance
Date2026-11-23

Original source: LK-PQC-Hunter's PKC Forum post

The reference RS_encode copies its input into one static workspace, encodes in place and copies the result out (g_rs_workspace, Sigurd-128/sig_core.c:55,640–745); the verifier calls it on the signature's w polynomial (:1071). The optimized sig_verify runs the whole verifier on a static g_cached_verifier_workspace and reads a static per-key cache (SIG_AlgorithmInstance.c:70–74,622,664,679). Nothing locks this state. The ICCS API does not promise thread safety.

With four threads each verifying its own honest signature, about 77% of verifications failed in the reference Sigurd-128 and about 90% in the optimized tree, with the submitted flags and with GCC 15.2 and Clang 21.1. Every single-thread control passed. The optimized tree also terminated: sig_hash_ctx_update aborts on its capacity check (sig_core.c:193–197), and a worker thread segfaulted in raw_collect_nonzero_terms (:347). When all threads shared one key and genuine signature, the optimized tree accepted that signature for a message with one bit flipped 27 times in 28,000 such calls; single-threaded, all 27 were rejected. With different keys in the threads, and in the reference tree, no altered input was accepted. Whether other messages can be accepted the same way was not tested.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

sh sign-24/reproduce_thread_race.sh

The witness checks the static workspaces in all six trees, builds the reference Sigurd-128 in a temporary directory with the Makefile's CFLAGS, and prints failed and total honest verifications for one thread and for four threads. The count varies between runs. It then builds the optimized Sigurd-128 with the Makefile's OPT_CFLAGS (skipped without AVX2) and runs 32 child processes in which, for 500 rounds, three threads verify the genuine message and a fourth verifies the same signature on the message with one bit flipped; it prints how often the altered message was accepted, the single-thread controls and how many children aborted or segfaulted. In one run, 89 of 15,565 altered verifications were accepted and 2 of the 32 children aborted. The whole witness takes under a minute.
