kem-17-1: Publicly reproducible secret keys

SeverityCritical
Scopeimplementation
StatusConfirmed
AffectedReference implementation, all four parameter sets
DiscoveryTrivial
ExploitationTrivial
CreditMarkku-Juhani O. Saarinen markku-juhani.saarinen@tuni.fi, with AI assistance
Date2026-09-21

Key generation draws from a file-scope SHAKE-256 PRNG context that is never initialized by the KEM wrapper. The API-provided seeded DRNG is declared but never consumed. Each fresh process therefore begins from the same zero-initialized state and generates the same key pair.

Fresh-process tests with different API seeds produced identical public and secret keys for hep-qc-1, hep-qc-3, hep-qc-5, and hep-qc-7.

An attacker recovers a victim's secret key by starting a fresh process and invoking the submitted key-generation API once. No code-based cryptanalysis is required. The resulting secret key decapsulates the victim's ciphertexts, completely breaking the claimed KEM confidentiality.

The wrapper must initialize its PRNG from the supplied DRNG for every independent key-generation operation and must not rely on zero-initialized global state.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

Build the candidate and the reproducer, then run:

make -C api harness && make -C tools && make -C kem-17
tools/ngcc_attack keygen-fresh kem-17/lib/libhep-qc-1.so 0x01   # repeat with a different seed

tools/reproduce.sh runs this together with the other supported runtime witnesses and their controls. See tools/README.md.

kem-17-2: HEP-QC-7 has at most 256 bits of key-generation support

SeverityCritical
Scopedesign
StatusConfirmed
AffectedHEP-QC-7 specification
DiscoveryTrivial
ExploitationApproximately 2^256 key-generation trials
CreditMarkku-Juhani O. Saarinen markku-juhani.saarinen@tuni.fi, with AI assistance
Date2026-09-21

This is independent of the implementation defect above. The HEP-QC-7 specification claims 512-bit classical security, but fixes seedKEM, every derived seed, and the shared key K at 32 bytes. KEM.KeyGen samples one 256-bit seedKEM and deterministically derives seedPKE and the complete PKE key pair from it.

There are consequently at most 2^256 HEP-QC-7 public keys. A generic attacker can enumerate seedKEM, regenerate the encapsulation key, and compare it with the target public key. A match supplies the corresponding decapsulation key. The 32-byte KEM output also has at most 256 bits of delivered-key capacity.

This is a specification-level parameter-selection break of the advertised 512-bit classical level. It is not made less valid by the submitted wrapper's much cheaper predictable-key failure; repairing the wrapper still leaves this 2^256 design ceiling.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

Specification evidence is on physical PDF pages 12–14. Run:

python3 security/design_parameter_audit.py --report-id kem-17-2

kem-17-3: First encapsulation in each process is publicly reproducible

SeverityCritical
Scopeimplementation
StatusConfirmed
AffectedReference implementation, all four parameter sets
DiscoveryTrivial
ExploitationTrivial for the first encapsulation in a fresh process; later-session recovery from two consecutive public ciphertexts has an analytic upper bound of 2^80 trials
CreditMarkku-Juhani O. Saarinen markku-juhani.saarinen@tuni.fi, with AI assistance; consecutive-session extension by Hao Yan, Yuhang Cao, Yao Tong, and Qiaosheng Zhang (Shanghai AI Lab; AI-assisted discovery, human verified)
Date2026-09-21

Follow-up source: Hao Yan and coauthors' PKC Forum analysis, 2026-10-26

kem_enc draws both its message m and salt consecutively from a file-scope SHAKE-256 PRNG context. The wrapper never initializes that context from the API-provided DRNG, so it begins in the same zero-initialized state in every fresh process.

For a fixed public key, the first encapsulation in each fresh process consequently repeats both the ciphertext and shared secret. An attacker can run the public encapsulation algorithm in a fresh process with the recipient's public key and recover the exact first session key produced by another fresh process. Fixing key generation alone does not repair this independent KEM confidentiality failure.

The follow-up identifies a second failure in the same encapsulation generator. Its context is a 208-byte array, but each update writes only the first 26 bytes (common/symmetric.h:41–44, common/symmetric.c:111–116). The output and next-state calls use the same input to the prefix-consistent pseudoXOF. Thus the 16-byte salt in each ciphertext is the first 16 bytes of the next state, leaving only 10 unknown bytes. Given two consecutive ciphertexts from one stream, with no intervening generator calls, an observer can enumerate at most 2^80 states consistent with the first salt, check them against the second salt, and derive the second encapsulation's message and shared secret. This route also applies if the generator is initialized with an unknown seed. The full search was not run; its bound follows from the submitted source and the native check below. Reclassified scope on 2026-10-26; severity and status are unchanged.

Every encapsulation operation must obtain fresh entropy from the API DRNG or initialize a per-operation generator from it. Message and salt generation must not use predictable global state.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

In all four parameter sets, kem_enc calls prng_get_bytes(m, ...) and then prng_get_bytes(salt, ...); the wrapper declares the initialized API DRNG but never uses it. The permanent witness compares fresh processes with different API seeds:

tools/reproduce.sh kem-17

It reports identical first public-key, ciphertext, and shared-secret digests for HEP-QC. The Aigis-Enc+ control differs across the two seeds.

The native generator check runs the unmodified reference encapsulation:

sh kem-17/reproduce_prng_state_leak.sh        # optional argument: search bits (default 16)

For each parameter set, it checks that the context stays zero beyond 26 bytes and that the first ciphertext's salt equals the next state's prefix. It then searches the low 16 of the 80 unknown state bits, taking the other 64 from the true state as a scaling hint. The recovered state must regenerate the second ciphertext and shared secret, and the holder's decapsulation must agree. A flipped first salt yields no candidate. The CTX_LEN = 26, SALT_BYTES = 16 state-update code is shared by all four reference sets, and the full 2^80 search is not run.

kem-17-4: Public column multiplicities break the EPC-P assumption

SeverityHigh
Scopedesign
StatusConfirmed
AffectedAll four HEP-QC parameter sets
DiscoveryModerate
ExploitationLinear-time distinguishing; claimed structure recovery takes seconds to minutes
CreditTianyuan Xie
Date2026-09-22

Original source: NGCC PKC Forum report

HEP-QC repeats every column of its inner Reed–Muller generator MULT = n2/128 times before applying row mixing and a column permutation. Those operations preserve equality. The public matrix G' therefore has exactly n1*128 column classes of multiplicity MULT and 64 singleton columns, whereas a uniform matrix has no repeated columns except with negligible probability. This gives a public, linear-time distinguisher with advantage essentially one and directly falsifies the EPC-P assumption used by the specification's first security bound.

Tianyuan Xie's mailing-list analysis additionally reports recovery of the affine blocks and exact secret transformation T on 35/35 official keys. The remaining frame-label searches are estimated at 2^84.1, 2^131.0, and 2^198.7 for HEP-QC-1, -3, and -5, below their 128-, 192-, and 256-bit claims. The public attachment reproduces the distinguisher, but not the full transformation recovery, so those residual key-recovery costs are less independently reproducible than the confirmed EPC-P break.

Xie also identifies an independent gap in Theorem 6.3.1's EPC-P-only IND-CPA bound: replacing G' by a uniform matrix in Game 2 does not make the challenge ciphertext independent of the selected message. For fixed public s, the noise s*r2 + e has at most binomial(n,omega_r)*binomial(n,omega_e) possible values before truncation. Its translates by two messages' codewords are therefore almost surely disjoint for a uniform G' (their expected overlap is bounded by the square of that support size divided by 2^(n1*n2)). Thus the claimed statistical independence is false. This finite-support argument does not give an efficient ciphertext distinguisher; a computational assumption about the noise distribution is still needed. It is a proof gap, not a separate demonstrated KEM break.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

make -C kem-17 lib/libhep-qc-1.so
python3 kem-17/reproduce_epcp_fingerprint.py

On a freshly generated official HEP-QC-1 key, this prints 3^5888 + 1^64; its uniform-matrix control prints 1^17728.

kem-17-5: Secret permutation and mixing matrix drive memory and control flow

SeverityMedium
Scopeside-channel
StatusConfirmed
AffectedReference and x86_64 implementations, all parameter sets
DiscoveryModerate
ExploitationLocal cache/control-flow observation; no full key recovery demonstrated
CreditMarkku-Juhani O. Saarinen markku-juhani.saarinen@tuni.fi, with AI assistance
Date2026-09-23

HEP-QC decapsulation regenerates private y, mixing matrix t, and column permutation p from the secret seed (ref/PKE_HEP_QC.c:185-220). The permutation indexes output memory by P[old_col] (common/vector.c:498-503,477-485). The code then inverts private t using a value-dependent pivot search and conditional row operations (common/vector.c:369-408). These addresses and branches disclose information about secret key material to a sufficiently close observer. No remote channel, complete key recovery, or shared-secret extraction is demonstrated.

The same decapsulation key expansion also runs secret-seed rejection sampling, retry-until-invertible matrix generation, and a Fisher–Yates x % bound with hardware division in the reviewed GCC -O2 build (common/parsing.c:23-31, common/vector.c:64-76,343-357,416-423). These are additional paths within this finding, not separate demonstrated key-recovery attacks.

Constant-time fix (moderate, hence Medium): apply the secret permutation obliviously with a Beneš network, as Classic McEliece does, invert the mixing matrix with masked-pivot constant-time elimination, and replace the rejection sampling, the retry-until-invertible loop and the division-based Fisher–Yates shuffle with fixed-work constant-time equivalents. These are well-known techniques with moderate cost, although several components change.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

The source-level witness is ref/KEM_HEP_QC.c:165-212 → ref/PKE_HEP_QC.c:185-220 → common/vector.c:369-408,477-503 under Implementations/Implementations/; the x86_64 PKE source calls the same shared routines. See constant_time.md for the secret/public mapping. This is not a measured timing benchmark.

kem-17-6: Every seed expansion passes through a 208-bit XOF state

SeverityCritical
Scopeimplementation
StatusConfirmed
AffectedHEP-QC-5 (256-bit) and HEP-QC-7 (512-bit); reference and x86_64 implementations. HEP-QC-1 and -3 have the same state but no shortfall
DiscoveryModerate
ExploitationAbout 2^208 key-expansion trials recover a decapsulation key from its public key, and about 2^208 encryption trials recover a shared secret from a ciphertext; not run
CreditMarkku-Juhani O. Saarinen markku-juhani.saarinen@tuni.fi, with AI assistance
Date2026-11-15

The scheme's XOF context is declared as 26 64-bit words, 208 bytes (common/symmetric.h:42–44). xof_init fills it with pseudoXOF(CTX_LEN * 8, seed, …) and xof_proc refreshes it the same way (common/symmetric.c:43,115). CTX_LEN is 26 and the first argument of pseudoXOF is a bit length, so both calls write 208 bits. The other 182 context bytes stay zero. Every stream the XOF produces is therefore a function of a 208-bit state, whatever the seed length.

Key generation expands the whole PKE decryption key from this XOF: the vectors y and x, the mixing matrix and the permutation all come from xof_init(&dk_xof_ctx, dk_pke, SEED_BYTES) (common/parsing.c:26–30). An attacker can enumerate the 2^208 states, expand each candidate key and compare the resulting public syndrome with the public key. Encryption draws its sparse vectors from the same XOF under θ, so a ciphertext likewise has at most 2^208 possible randomness streams, each checkable against u. Both searches are below the 256-bit target of HEP-QC-5 and the 512-bit target of HEP-QC-7.

The defect is in the submission's own wrapper and holds for an ideal pseudoXOF with the same arguments. It is separate from the 256-bit seed of kem-17-2, which concerns only HEP-QC-7, and from the generator instance of kem-17-3.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

sh kem-17/reproduce_xof_state_width.sh

The witness checks the two 208-bit calls, CTX_LEN in all eight parameter files and the key-expansion call. For each reference parameter set it then initialises the archived XOF, requires the context to be zero beyond byte 26, and requires three 4,096-byte squeezes to be reproduced from those 26 bytes alone. The 2^208 searches are not run.

kem-17-7: The 3-DQCSD-P assumption leaves the second syndrome's fixed parity unrestricted

SeverityMedium
Scopedesign
StatusConfirmed
AffectedAll four HEP-QC parameter sets; the second IND-CPA bound of Theorem 6.3.1
DiscoveryTrivial
ExploitationOne parity computation distinguishes the assumed distribution with advantage 1/2; no message or key recovery demonstrated
CreditXifeng Jin (CertiK), with AI assistance
Date2026-11-15

Original source: Jin's PKC Forum post

Definition 2.3.14 (physical p. 9) samples a matrix with circulant blocks h1 and h2 of parities b1 and b2 and three vectors of weight ω, and outputs the syndromes y1 = x1 + h1·x3 and y2 = x2 + h2·x3. Definition 2.3.15 asks to distinguish these from the uniform distribution over F^n_{2,b3} × F^n_2. The first syndrome is restricted to its parity b3 = ω + b1·ω. The second is not restricted at all.

In F_2[x]/(x^n − 1) parity is evaluation at x = 1 and is multiplicative, so every real sample has parity(y2) = ω + b2·ω (mod 2). A uniform y2 has that parity with probability one half. Checking one bit therefore solves the problem with advantage 1/2. In the reduction that uses the assumption (physical p. 26) the second syndrome is e + s·r2, with parity ω_e + b2·ω_r, again fixed and public: 1 + b2 for HEP-QC-1, -5 and -7 and 0 for HEP-QC-3.

The assumption is false as defined, so the bound Adv_2-DQCSD-P + Adv_3-DQCSD-P of Theorem 6.3.1 (physical p. 23) says nothing. The specification's remark that zero-padding this component costs no security (physical p. 30) does not address parity. This invalidates the stated proof route. It does not by itself distinguish encrypted messages or recover a key: a ciphertext adds a codeword to this component, and the submitted code transmits only its first n1·n2 bits. Hence Medium.

Reproducing

Commands below run in a checkout of the ngcc-harness repository with the candidate built (see its README).

python3 kem-17/reproduce_second_syndrome_parity.py

The witness checks the wording of Definition 2.3.15 and the four parameter files, then samples the real second syndrome in F_2[x]/(x^n − 1) 24 times for each parity of s and each parameter set. It requires the predicted constant parity in every sample, and both parities in a uniform control.

kem-17-8: Every encapsulation and decapsulation leaks the mask matrix, and decapsulation reads past a short ciphertext

SeverityLow
Scopeimplementation
StatusConfirmed
AffectedHEP-QC-1, -3, -5 and -7; reference and x86-64 implementations (identical by source; the witness runs the reference)
DiscoveryTrivial
ExploitationUnbounded memory growth of 0.28 to 12.6 MB per call in a long-running process, and an out-of-bounds read of a caller-supplied short ciphertext; no disclosure shown
CreditLK-PQC-Hunter (NGCC PKC Forum sender), using the LKQ PQC Hunter automated tool
Date2026-11-19

Original source: LK-PQC-Hunter's PKC Forum post

hep_qc_pke_encrypt allocates G_mask with calloc (PKE_HEP_QC.c:120) and never frees it. Encapsulation encrypts once and decapsulation re-encrypts, so every kem_enc and every kem_dec, honest or tampered, leaks one block of 283,648, 861,696, 1,845,248 or 12,619,776 bytes at the four sets; key generation leaks nothing. kem_dec also discards ct_len_bytes: an honest HEP-QC-1 ciphertext in a heap buffer one byte short, declared at that length, is read past its end in hep_qc_c_kem_from_string (parsing.c:79) under AddressSanitizer, while the full-length buffer is clean.
