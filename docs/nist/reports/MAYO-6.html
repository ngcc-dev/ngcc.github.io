MAYO-6 — Low: extended Schur--Macaulay model puts five Table 2.2 additional MAYO sets below target

Result

Peigen Li and Siyong Tao's Extending the Schur--Macaulay Framework for UOV Attacks via Truncated Polynomial Algebras (posted 2026-10-11, revised 2026-11-17) reformulates Merz and Ran's Schur--Macaulay divided-power attack in multigraded p-truncated polynomial algebras and applies the characteristic-two model (Table 4, p. 25) to seven additional parameter sets from MAYO-spec.pdf Table 2.2 (physical p. 20).

Running a Python port of the authors' published Magma estimator (Complexity.magma and Math.magma, commit a292e4c7) across all four Table 2.1 main sets and all 28 Table 2.2 additional sets with o <= 33 (in the paper's free-memory RAM-gate model, 3 * rho * H^2 * 36 bit operations matching MAYO's 36-bit-operation GF(16) convention) shows that for the four main implemented parameter sets in Table 2.1, the estimator finds no admissible tuple (MAYO1, MAYO3, MAYO5) or stays above target (MAYO2), while five Table 2.2 sets fall 2.8 to 41.7 bits below their claimed Category 3 (207) and Category 5 (272) targets at r = 1 (and one additional Category 1 Table 2.2 set, (77, 66, 11, 6), reaches 142.41 at r = 0, 0.59 bit below 143, versus 145.19 at r = 1):

In the companion paper Attacking UOV-based Signatures over divided power algebras (Li and Tao, revised 2026-11-14, Table 4), the single-variable divided-power wedge attack applies only to Table 2.2 sets with o >= 30 and leaves all evaluated MAYO sets above target (214–215 bits at Level III and 278 bits at Level V).

Estimator discrepancies, unbalanced regime, and modeling limits

  1. Unbalanced projection caveat. Remark 6.4 (p. 24) states that the authors restrict their analysis to balanced projection down because they have not obtained an effective Hilbert-series estimate for unbalanced projection. Every below-target estimate in Table 4 and in Complexity.magma (schtwocplx) nevertheless uses an unbalanced tuple (k1 = 0 < k2). Restricting schtwocplx to balanced projection k1 = k2 (with fixed degrees d1 = d2 = o - k, which is not a search over arbitrary balanced degrees) gives 227.43–243.03 bits at Level III and 289.87–324.64 bits at Level V (and 166.21 for (77, 66, 11, 6)), all above target.
  2. Discrepancies between Table 4 and the authors' Magma estimator. Six of the seven Table 4 rows reproduce their printed floored bit costs in Complexity.magma at k2 + 1 (and d2 - 1) rather than the printed (k2, d2) (and (112, 98, 14, 7) prints d1 = 17 > o = 14, whereas schtwocplx evaluates (0, 8, 14, 6) at 198.71). The seventh row, (152, 136, 16, 9), reproduces 281 at its printed tuple (0, 3, 16, 13) only with r = 0 (281.39), not the paper's stated r = 1 (285.17 at (1, 2, 15, 14), whereas Complexity.magma prints (0, 3, 16, 13) at 285 because it compares floored costs with <= and keeps the last tie).
  3. Conjectural rank premise and retained toy checks. The solving-degree criterion relies on unproven Hilbert-series and structured-rank conjectures (Conjecture 3.11 and Eq. 5.2), with no full-scale experiments. The retained SageMath toy script analysis/unbalanced_schur_toy.sage checks small unbalanced GF(16) UOV instances (n = 7..9, o = 4, k2 = 1..3): all ten tested instances with Sto <= 0 achieved exact corank one (nullity = 1), while two positive-Sto toys departed from Sto in opposite directions — (n=8, o=4, m=2, k2=2) gave nullity = 72 versus Sto = 59, and (n=7, o=4, m=4, k2=1) gave nullity = 1 despite Sto = 221 > 0. Thus Sto is not an exact dimension identity in the unbalanced regime, and Sto > 0 alone does not prove that the attack fails (so for MAYO1, MAYO3, and MAYO5, the estimator finding no admissible tuple is a negative result of this model rather than a proof of immunity).
  4. Unaccounted memory cost. Remark 6.3 explicitly omits memory. One block-Wiedemann vector holds H GF(16) elements (2^88.6 to 2^124.8 bits for the five r = 1 below-target sets; storing the sparse matrix requires roughly 2^104 to 2^141 bits). For (152, 132, 19, 7) at 230.33 RAM bits (log2(H) = 103.01), a logarithmic memory factor still leaves roughly a 35-bit shortfall, whereas a 2D-mesh sqrt(memory) penalty pushes the cost above 272 bits. Under NIST's call §4.B.3, a RAM-only estimate without memory accounting is not a settled category break.
  5. Scope limited to Table 2.2 showcase sets. None of the affected tuples is among the four submitted and implemented parameter sets in Table 2.1 (MAYO1, MAYO2, MAYO3, MAYO5). Table 2.2 lists them as additional trade-off parameter sets in the pinned Round 3 specification.

Classification

Low / Lead / Design. The calculation is candidate-specific, reproduces all seven Table 4 floored bit costs from the authors' published Magma estimator (plus the full Table 2.2 sweep for o <= 33), and puts five Table 2.2 trade-off sets 2.8 to 41.7 bits below their claimed RAM-gate targets at r = 1 (plus one Category 1 set by 0.6 bit at r = 0). It remains a Lead rather than a confirmed category break because every below-target point sits in the conjectural unbalanced regime (k1 = 0 < k2), omits 2^89–2^141-bit memory costs, executes no full-scale attack, and for all four main implemented sets the estimator finds no admissible tuple or stays above target.

Reproduction

python3 MAYO/reproduce_mayo_6.py

The standard-library script pins MAYO/MAYO-spec.pdf and ports Complexity.magma and Math.magma (commit a292e4c7) to sweep all four Table 2.1 main sets and all 28 Table 2.2 additional sets with o <= 33 (both unbalanced and balanced k1 = k2 at r = 0, 1), verifying all seven Table 4 floored bit costs, all six off-by-one (k2, d2) rows, and the (152, 136, 16, 9) r = 0 row. It is a deterministic cost/model check, not a key-recovery run. With SageMath, run the small GF(16) unbalanced toy checks with:

sage MAYO/analysis/unbalanced_schur_toy.sage

Harness reproduction

From the ngcc-harness checkout, run the pinned source script through the harness-side dispatcher:
